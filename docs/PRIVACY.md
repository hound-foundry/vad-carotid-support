# Privacy principles and build requirements

This is a design specification, not a privacy notice, data protection impact assessment or legal opinion. No production privacy review has been completed.

The initial product is intended to collect as little information as possible. No account, advertising, behavioural analytics, third-party health SDK, remote note sync or message board is in scope. The appointment sheet stores selected prompt IDs and an optional note; the support-preferences sheet stores selected preference IDs and an optional note. Each is stored only after the user presses Save. The reading list stores guide slugs only after the user chooses to save a guide. Saved topics can still reveal a person's interests to someone with access to the device or browser profile. Free-text notes may contain personal information.

The web build uses the current browser profile’s `localStorage`. This storage is not encrypted by the app and may be accessible to people or software that can use the profile or device; browser backup and sync settings vary. Native builds use Expo SecureStore and the platform keychain/keystore; operating-system backup and device access behavior still varies. Neither storage method guarantees privacy. Appointment notes are limited to 500 characters and support-preferences notes to 300 characters. Personal and milestone cards use separate versioned keys and bounded user-entered fields; cards may include medicines, contacts and dates only when the user chooses to enter them. Each tool offers explicit deletion, and the About page offers a confirmation-protected clear-all action for sheets, cards, accessibility preferences and saved-guide links. Export occurs only after an explicit preview action: web cards generate PDF/text and milestone PNG locally; native adapters use platform print/share dialogs and still need device verification. Copies sent to another app, printed, uploaded to a social platform, or backed up are outside this app’s deletion control. Cards are personal information aids, not official medical records or emergency plans; users must check their contents before sharing.

Unsaved sheet and card edits stay only in app memory through in-app navigation. Guide reading position, local reading pace and library search also stay in session memory; they are not automatically saved. Reloading or closing loses these unsaved states. Saved items show generic labels rather than notes or card contents. Clear all waits for pending sheet saves before removing the six project keys, then clears sheet and reading memory. PDF generation requests only bundled same-origin code/fonts, never the entered fields. No date filters the entered event/milestone date from every output; it does not remove the practical card's generated last-updated date. See [the data-flow inventory](DATA_FLOW.md) and [observed synthetic checks](DESIGN_CASE_STUDY.md).

The source has no analytics, network sync, account, or backend. Static content and references are bundled at build time; external publishers are contacted only when a user opens their link. This must be rechecked against the final hosting, DNS/CDN, dependency and distribution setup.

Sensitive content must not enter URLs, referrers, browser logs, analytics, crash dumps or share URLs. Do not claim local storage alone ensures privacy. The app code contains no logging of appointment or support-preferences sheet content or saved guide slugs. Review this property again if logging, crash reporting, sync, hosting or third-party SDKs are introduced.

The website can still generate server logs and expose visitors to external-link tracking when they leave the site. Review hosting, DNS/CDN, error handling, dependency and store data disclosures. Link out with clear destination labels; do not embed third-party pages. Use no cookies and keep device storage limited to the appointment sheet, support-preferences sheet, saved guide slugs, two cards and display preferences documented above; assess the applicable storage rules before release.

Before launch, determine the real operator/controller, contact route, lawful bases, special-category conditions where relevant, records, rights handling, breach response, vendor agreements, international transfers and any required regulator fee or registration. A free or volunteer project is not automatically exempt from data protection law.
## Static-host headers

The web bundle includes `public/_headers` with a minimal deployment baseline: MIME sniffing protection, a strict-origin referrer policy, and disabled camera, microphone and geolocation permissions. A hosting provider may require different syntax or additional headers; verify the deployed response headers before launch. Do not add analytics, a backend or third-party embeds without repeating the privacy and security review.
