# Privacy principles and build requirements

This is a design specification, not a privacy notice, data protection impact assessment or legal opinion. No production privacy review has been completed.

The initial product is intended to collect as little information as possible. No account, advertising, behavioural analytics, third-party health SDK, remote note sync or message board is in scope. The appointment sheet stores selected prompt IDs and an optional note; the support-preferences sheet stores selected preference IDs and an optional note. Each is stored only after the user presses Save. The reading list stores guide slugs only after the user chooses to save a guide. Saved topics can still reveal a person's interests to someone with access to the device or browser profile. Free-text notes may contain personal information.

The web build uses the current browser profile’s `localStorage` for wording and preferences, and a separate IndexedDB store for explicitly saved card photos. Neither is encrypted by this app. People or software that can use the profile or device may have access; browser backup and sync settings vary. Native wording uses Expo SecureStore and the platform keychain/keystore; native photos and designed exports need separate implementation and device verification. Neither storage method guarantees privacy. Appointment notes are limited to 500 characters and support-preferences notes to 300 characters. Personal and milestone cards retain their separate v1 keys and bounded user-entered fields. Cards may include medicines, contacts and dates only when the person enters them. Delete and the About page's confirmed clear-all include saved photos. Web PDF, PNG, print and text generation occurs locally after an explicit preview action. Copies downloaded, printed, shared, uploaded or backed up are outside this app’s deletion control. Cards are personal information aids, not official medical records or emergency plans; users must check their contents before sharing.

Unsaved sheet and card edits, including selected photos, stay only in app memory through in-app navigation. Guide reading position, local reading pace and library search also stay in session memory. Reloading or closing loses unsaved states. Saved-item labels do not expose notes, names or medicines. Clear all waits for pending sheet/card/photo saves before removing the six project keys and the photo resource, then clears session memory. Generation requests only bundled same-origin code, fonts and public artwork; entered fields and private photos are never sent with these requests. No date filters the entered event/milestone date from every output; it does not remove the practical card's generated last-updated date. See [the data-flow inventory](DATA_FLOW.md) and [card collection validation](DESIGNED_CARDS.md).

Photo input accepts JPEG, PNG and WebP up to 10 MB. The browser decodes orientation and re-encodes an opaque JPEG locally, removing source metadata and filenames and limiting the longest edge to 1280px. New photos are not stored before Save. Saved card JSON contains only an opaque photo ID and crop values; the JPEG Blob is held in `dissection-companion-card-photos`, store `photos`, with a separate personal/milestone owner. Replacement saves coordinate the new Blob, wording and removal of the old Blob. A failure preserves the draft and attempts rollback; incomplete rollback/deletion is reported as a failure. Browser quotas and eviction can still remove local data. Missing photos are reported rather than silently omitted from a visual download. The text alternative excludes photos.

The source has no analytics, network sync, account, or backend. Static content and references are bundled at build time; external publishers are contacted only when a user opens their link. This must be rechecked against the final hosting, DNS/CDN, dependency and distribution setup.

Sensitive content must not enter URLs, referrers, browser logs, analytics, crash dumps or share URLs. Do not claim local storage alone ensures privacy. The app code contains no logging of appointment or support-preferences sheet content or saved guide slugs. Review this property again if logging, crash reporting, sync, hosting or third-party SDKs are introduced.

The website can still generate server logs and expose visitors to external-link tracking when they leave the site. Review hosting, DNS/CDN, error handling, dependency and store data disclosures. Link out with clear destination labels; do not embed third-party pages. Use no cookies and keep device storage limited to the sheets, guide slugs, two cards, their optional photos and display preferences documented above; assess the applicable storage rules before release.

Before launch, determine the real operator/controller, contact route, lawful bases, special-category conditions where relevant, records, rights handling, breach response, vendor agreements, international transfers and any required regulator fee or registration. A free or volunteer project is not automatically exempt from data protection law.
## Static-host headers

The web bundle includes `public/_headers` with a minimal deployment baseline: MIME sniffing protection, a strict-origin referrer policy, and disabled camera, microphone and geolocation permissions. A hosting provider may require different syntax or additional headers; verify the deployed response headers before launch. Do not add analytics, a backend or third-party embeds without repeating the privacy and security review.
